# Concrete bug hunt on the money path (adversarial, line-level)

## Summary
The money path is unusually well hardened for an MVP: I traced the consensus gate, spend caps, order-placement, and vote parsing adversarially and could not find a fail-OPEN — every error, abstain, unparseable vote, unknown mode, and exception blocks the trade rather than shrinking quorum or falling back to a lone vote. The concrete defects I did find are ledger/accounting integrity issues rather than money-loss holes: a missing dedup of `--coins` that double-writes the execution ledger for a single idempotent order, plus several spend-cap tally imprecisions. None of these can place an unintended trade; the worst corrupts the ledger-derived position for a specific malformed input. Findings are ranked most-severe first.

## Strengths
- Consensus gate fails closed everywhere I probed: sub-quorum (<2 votes), any abstain under REQUIRE_CONSENSUS, split votes, tiebreaker==primary, tiebreaker-absent, unknown llm_mode, and any exception in the multi-LLM block all return a BLOCKED PanelDecision with action=None (crypto_trading_bot.py:1299-1342, 1396-1402) — never a silent fallback to the primary's solo vote.
- The what-if CEX path never reaches trader.market_order_buy — buy_something's first branch (crypto_trading_bot.py:1572) records a synthetic 'simulated' fill and returns, so a mode mixup cannot place a real order.
- Idempotency is real and correctly leveraged: deterministic client_order_id = run_id-coin-buy (coinbaseutil2.py:150-162) plus the intent-row-before-order write sequence (buy_something) means a retried buy dedupes at Coinbase and leaves a reconcilable stub on crash.
- Coinbase string-numeric fields are coerced defensively via _to_float/_as_float (tolerate None and ''), and the fee read prefers total_fees with a safe fall-back to fee (coinbaseutil2.py:345-349), matching the documented gotcha that fee is often ''.
- Timestamp discipline is correct on the money path: executionledger and historyutil both use datetime.now(timezone.utc).replace(tzinfo=None).isoformat()+'Z' and marketdata uses aware datetime.fromtimestamp(t, tz=timezone.utc) — no naive .timestamp() misuse (the documented lp_history 4h-bug pattern is absent here).
- voteschema.parse_vote fails closed on the money path: empty text, invalid JSON, schema violation, and symbol-mismatch all map to an Abstain, and a validated BUY with garbage reasons is rejected rather than traded.

## Findings

### [MEDIUM/S] Duplicate coins in --coins are not deduplicated, double-writing the execution ledger for one idempotent order (doubled position + daily-cap tally)
**Evidence:** ANALYZE_COINS is built without dedup: `ANALYZE_COINS = [c.strip().upper() for c in ANALYZE_COINS_RAW.split(',') if c.strip()][:5]` (crypto_trading_bot.py:2077), whereas the discovery path DOES dedup via a `seen` set (crypto_trading_bot.py:2472-2485). So `--coins=BTC,ETH,BTC` analyzes BTC twice. Each maybe_execute_buy->buy_something call writes a fresh intent row (executionledger.append_intent mints a NEW ledger_id every call, crypto_trading_bot.py:1561) but rebuilds the SAME deterministic client_order_id `f"{run_id}-{coin}-buy"` (coinbaseutil2.py:160-161). Per AGENTS.md:87 (validated live) a duplicate client_order_id returns success:true with the ORIGINAL order_id and NO second fill, and _poll_fill then reports that order FILLED — so record_fill writes a second 'filled' row (ledger_id L2, same order_id, same filled_size). positions_from_rows sums filled_size across every FILLED row joined by ledger_id with no order_id dedup (executionledger.py:250-262), and intended_spend_on_date sums every live INTENT row (executionledger.py:324-341).

**Impact:** For a single real fill, the ledger records two intent rows and two 'filled' rows sharing one order_id. The bot's attributed position for that coin is doubled (feeds scripts/reconcile_positions.py, producing a phantom shortfall/drift vs the account), and the daily LIVE spend cap is charged 2x notional for 1x actual spend. No double spend occurs (Coinbase idempotency protects the money), but the ledger-derived position — real per-user data — is corrupted. Trigger is an operator typo in --coins; discovery mode is immune because it already dedups.

**Recommendation:** Deduplicate ANALYZE_COINS preserving order at crypto_trading_bot.py:2077, e.g. `ANALYZE_COINS = list(dict.fromkeys(c.strip().upper() for c in ANALYZE_COINS_RAW.split(',') if c.strip()))[:5]`. Defense-in-depth: have positions_from_rows and the daily-cap sum collapse fill rows by order_id (the AGENTS.md:87-documented duplicate signal is order_id identity vs the ledger, which is currently not implemented anywhere in the record/position path).

### [LOW/S] Run-summary 'Blocked by spend cap' tally omits daily-cap refusals (already-documented)
**Evidence:** The daily-cap refusal path just prints and returns without incrementing any counter (crypto_trading_bot.py:1639-1644), while only the per-run cap increments spend_tracker.blocked (SpendTracker.try_spend, crypto_trading_bot.py:1507). The run summary reports only that counter: `print(f"Blocked by spend cap: {spend_tracker.blocked}")` (crypto_trading_bot.py:2618). This is exactly acceptance issue #2, docs/ACCEPTANCE_RESULTS_2026-07-19.md:44-46 ('LINK refusal printed [DAILY CAP] but the summary showed 0'), and is labeled there as known/cosmetic.

**Impact:** In a run where the daily cap (the cross-run, ledger-backed cap) does the blocking, the end-of-run summary reports 'Blocked by spend cap: 0', understating refusals in precisely the live runs where the operator most relies on the summary to know a budget stopped a buy.

**Recommendation:** Add a distinct daily-cap-blocked counter (module global or on SpendTracker), increment it in the crypto_trading_bot.py:1639-1644 branch, and print both counts in the RUN SUMMARY (e.g. 'Blocked by run cap: X | Blocked by daily cap: Y').

### [LOW/S] Per-run spend is committed (and coin appended to summary) before the live exclude-list check, so an excluded coin consumes budget without an order
**Evidence:** In maybe_execute_buy the order is: run-cap commit `if not spend_tracker.try_spend(NOTIONAL_USD)` (crypto_trading_bot.py:1647, which does `self.spent += amount` on success), then `coinsToBuy.append(coin_symbol)` (1653), and ONLY THEN the live exclude check `if not WHATIF_MODE and coin_symbol in coinsToExclude: ... return` (1654-1658). coinsToExclude={'TRUMP'} (crypto_trading_bot.py:2238).

**Impact:** If the panel unanimously BUYs an excluded coin (currently TRUMP) in live mode, spend_tracker.spent is charged the notional and the coin appears in the 'Coins to buy' summary list, even though no order and no ledger row are created. This shrinks the remaining per-run budget for subsequent legitimate buys and makes the summary claim a buy that never happened. Direction is safe (over-blocks), but the accounting and summary are wrong.

**Recommendation:** Move the exclude-list check above the try_spend/append block (right after the WHATIF/DEX gating), so an excluded coin is skipped before any budget is committed or any coin is added to coinsToBuy.

### [LOW/M] Daily LIVE spend cap counts every intent row regardless of fill outcome and excludes fees
**Evidence:** buy_something writes the intent row via append_intent (crypto_trading_bot.py:1561) BEFORE placing the order (trader.market_order_buy at 1598), and intended_spend_on_date sums ALL INTENT rows with trading_mode=='live' for the date with no reference to whether the corresponding fill succeeded (executionledger.py:324-341), via live_spend_today (executionledger.py:353-361). There is no coupling to the fill row's status (FAILED/UNVERIFIED_FAILURE/UNCONFIRMED still leave the intent counted). Separately, the cap sums intended_notional_usd only — fees (~1.2%/side per AGENTS.md:82) are never added.

**Impact:** Two opposite imprecisions in the ledger-backed daily cap: (1) a live order Coinbase rejected (e.g. INSUFFICIENT_FUND) or that never confirmed still consumes daily-cap budget, so earlier failed attempts can refuse later legitimate buys (fail-closed, but surprising); (2) because the cap bounds pre-fee notional, the actual USD debited across a capped day exceeds the nominal cap by accumulated fees. Neither loses money, but a user reading '--daily-spend-cap-usd' as a bound on money leaving the account is misled in both directions.

**Recommendation:** Decide the cap's contract explicitly. Recommended: sum against intents whose latest fill is not a clean 'failed' (reuse latest_fill_by_ledger_id, executionledger.py:267-279) so rejected orders don't consume budget, and document that the cap bounds intended pre-fee notional (or add an estimated fee factor). At minimum, add a one-line note in the --daily-spend-cap-usd help text that failed-order intents count and fees are excluded.
