# Business logic & money-path design correctness

## Summary
The consensus/vote/quorum core is genuinely fail-closed and unusually well spec'd by tests: every abstain path (error, refusal, parse failure, symbol mismatch, dead client) blocks under REQUIRE_CONSENSUS, the live double-lock is a clean pure function, and the intent-before-order ledger with F2 recovery is thoughtful for an MVP. The weaknesses are one layer out from the vote math: the ledger's integrity model has three real holes (the empirically-documented Coinbase duplicate shape is never detected on the write path so a duplicate resubmission double-counts a position; concurrent runs against the same history dir can silently lose ledger rows that the daily cap depends on; a corrupt JSON read silently resets the whole file on the next append), and the analyzer that the learning loop depends on violates the repo's own naive-timestamp contract, skewing every at-maturity grade by the machine's UTC offset and then freezing the wrong verdicts. Whatif is also a systematically optimistic predictor of live (no spread, no daily cap, no exclusion list), which matters because the owner's posture is live-day-one with whatif as the data engine.

## Strengths
- Fail-closed consensus is real, not aspirational: sub-quorum, any abstain under REQUIRE_CONSENSUS, unknown mode, tiebreaker==primary, tiebreaker-absent, and exceptions all return BLOCKED decisions (crypto_trading_bot.py:1299-1342, 1396-1402), and the ~60-case tests/test_consensus.py pins each path including the F1 standing-abstain machinery (register_client_init_failure keeps a dead client in quorum rather than pruning it, crypto_trading_bot.py:1032-1054).
- The live double-lock (resolve_trading_mode, crypto_trading_bot.py:1414-1461) is a pure, unit-testable truth table; any live request missing --live or LIVE_TRADING_CONFIRMED=1 downgrades loudly to whatif, and the downgrade is resolved before trader construction so the DEX wallet path is disarmed too (crypto_trading_bot.py:2016-2022).
- Order execution is written for the real, empirically-probed API: intent row before any order (buy_something, crypto_trading_bot.py:1561-1570), atomic fsync'd ledger writes (executionledger.py:92-106), create-response unwrapping per the verified nesting, recovery lookup on ANY create failure so an ambiguous timeout is never ledgered as a clean failure, and a distinct 'unverified_failure' state with an append-only reconcile --repair path (coinbaseutil2.py:222-284, scripts/reconcile_positions.py:90-135).
- voteschema.parse_vote is strict on every field, binds the vote symbol to the coin under analysis with a conservative whitelist (bind_symbol, voteschema.py:316-346), and fails closed when reasons debris dominates (voteschema.py:280-285) — the class of bug that spent real money in the 2026-07-18 eval is structurally closed.
- Spend-cap semantics are consistent and checked before any order: daily live cap summed from durable intent rows across runs (executionledger.py:324-341, 364-367), per-run cap exercised in whatif too, identical allow-exact-cap boundary on both (SpendTracker.try_spend crypto_trading_bot.py:1501-1510).
- The analyzer is honestly scoped (scorer only, no invented P&L), gives every record exactly one terminal category, separates live/whatif, excludes trading_mode='unknown' from scoring, and flags at-maturity vs degraded methodology per record (tradeanalyzer.py:57-87, 473-605).

## Findings

### [HIGH/M] Documented Coinbase duplicate shape (success + original order_id) is never detected on the write path; duplicate buys double-count positions in the ledger
**Evidence:** AGENTS.md:87 and tests/test_duplicate_rejection_shape.py:4-8 pin the live-validated behavior: resubmitting a client_order_id returns success:true with the ORIGINAL order_id, and state 'the duplicate signal is the returned order_id matching the ledger's row for that client_order_id'. No code implements that signal: coinbaseutil2.market_order_buy's recovery only runs on exception or success=false (coinbaseutil2.py:222-243); the real duplicate shape takes the normal success path and buy_something unconditionally appends a fresh 'filled' row (crypto_trading_bot.py:1596-1606) — it never loads the ledger or checks OrderResult.idempotent_reuse (grep: no consumer besides logging, coinbaseutil2.py:530). positions_from_rows then sums both fill rows (executionledger.py:250-262), doubling the position for one real order. Concrete trigger: ANALYZE_COINS is not deduplicated (crypto_trading_bot.py:2077 — '--coins=BTC,ETH,BTC' analyzes BTC twice, both buys share client_order_id 'run_X-BTC-buy'); a secondary trigger is RUN_ID's 1-second granularity (crypto_trading_bot.py:2028) colliding across two live launches.

**Impact:** The bot's attributed position and the analyzer's fill data are corrupted (2x size for one real order) with no error anywhere; a future SELL/exit path sized from ledger positions would try to sell holdings that don't exist. The exchange-side idempotency prevents double-spend, but the repo's own record of what it holds is wrong.

**Recommendation:** In buy_something's live branch (crypto_trading_bot.py:1596-1606), before executionledger.record_fill, load the ledger and check whether any prior fill row already carries result.order_id (or whether a prior intent row shares this client_order_id with a terminal fill); if so, record the fill with a 'duplicate_of': <ledger_id> field and teach positions_from_rows to count each distinct order_id at most once. Also dedupe ANALYZE_COINS at parse (dict.fromkeys before [:5]) and append a short random suffix to RUN_ID (keeps per-run determinism of client_order_id while eliminating cross-run collisions).

### [HIGH/M] No cross-process locking on executions.json/recommendations.json while the ops runbook schedules concurrent-capable runs against the real history dir
**Evidence:** executionledger._append_row is load -> append -> atomic replace with no lock (executionledger.py:109-114); historyutil.save_recommendation is the same pattern without even the atomic replace (historyutil.py:62-72). docs/RUNBOOK_whatif_cadence.md:133 installs a cron whatif run every 6h with HISTORY_DIR pointed at the REAL history/ ('so they point HISTORY_DIR at the real history directory', line 32), and runs take minutes (multi-provider, multi-round LLM calls plus the 6.5s LunarCrush throttle per call, marketdata.py:545). A manual or live run overlapping the cron run does concurrent read-modify-write on the same files: last writer wins and the other process's rows vanish.

**Impact:** Lost live intent rows silently shrink live_spend_today(), so the daily spend cap under-counts (fail-open on the one cap that spans runs); lost fill rows drop real fills from attributed positions. Lost recommendation rows corrupt the analyzer's dataset. All silent.

**Recommendation:** Wrap the read-modify-write in both executionledger._append_row and historyutil.save_recommendation with an exclusive lock (fcntl.flock on a sibling '.lock' file, held from load through os.replace). This is ~15 lines total and preserves the existing atomic-replace crash safety.

### [HIGH/S] Corrupt ledger/history JSON fails open: load returns [] on JSONDecodeError and the next append silently rewrites the file, wiping all prior rows and resetting the daily cap
**Evidence:** executionledger.load_executions catches json.JSONDecodeError/IOError, prints a warning, and returns [] (executionledger.py:79-89); _append_row then does rows=load_executions(); rows.append(row); _save_executions(rows) (executionledger.py:109-114) — a corrupt executions.json becomes a fresh 1-row ledger on the very next buy. historyutil has the identical pattern (historyutil.py:45-59, 62-72), and historyutil's non-atomic 'w' rewrite is itself a plausible corruption source on crash (acknowledged as weaker in executionledger.py's module docstring, lines 39-41). daily_cap_would_exceed reads through the same load (executionledger.py:353-367), so a wiped ledger reports $0 spent today.

**Impact:** A single corrupt read (partial historyutil write, disk hiccup, hand edit) destroys the entire money ledger or recommendation history the next time the bot writes, and simultaneously bypasses the daily live spend cap — the exact fail-open class the repo's core invariant forbids.

**Recommendation:** On load failure in executionledger (at minimum), fail closed: raise instead of returning [], and have buy_something/maybe_execute_buy treat an unreadable ledger as a refused buy. If graceful degradation is wanted, rename the unreadable file to executions.json.corrupt-<ts> before writing a fresh one so nothing is ever silently overwritten. Mirror in historyutil, and make save_recommendation use the same tmp+os.replace pattern executionledger already has.

### [HIGH/S] tradeanalyzer violates the repo's own naive-timestamp contract: when.timestamp() interprets naive UTC as local time, skewing every at-maturity grade by the machine's UTC offset
**Evidence:** tradeanalyzer.py:383-385: `target = when.timestamp(); closest = min(rows, key=lambda r: abs(r['time'] - target))` where `when` is a NAIVE UTC datetime (parse_timestamp, tradeanalyzer.py:107-121; maturity_time at 533) and rows carry true UTC epochs from Coinbase (marketdata.fetch_candles, marketdata.py:150-179). Python's naive .timestamp() assumes LOCAL time, so on the owner's non-UTC machine (pytrends is configured tz=360 = GMT-6, crypto_trading_bot.py:2007) the selected candle is ~5-6h off target. AGENTS.md:23 explicitly documents this exact trap ('Never compute epoch time via .timestamp() on a naive datetime... this was a real 4-hour bug in lp_history.py') — lp_history.py:109-123 was fixed; this instance was not. Worse, the windows become inconsistent: coin return spans [t_rec, maturity+offset] (rec_price is recorded at true t_rec) while the benchmark return spans [t_rec+offset, maturity+offset] (both endpoints via price_at), so the benchmark-relative excess is computed over mismatched windows, then frozen permanently by the sidecar state (tradeanalyzer.py:654-665).

**Impact:** Every AT_MATURITY-scored record is graded against wrong-time prices and a mismatched benchmark window, and the wrong verdicts are frozen so fixing the bug later does not repair them without a STATE_VERSION bump. The live/whatif learning loop — the stated reason for the whatif cadence — is fed corrupted win/loss data.

**Recommendation:** In CoinbasePriceProvider.price_at change to `target = when.replace(tzinfo=timezone.utc).timestamp()` (tradeanalyzer.py:383), add a regression test with a non-UTC TZ env, and bump STATE_VERSION to 3 so previously frozen at-maturity verdicts are re-scored.

### [MEDIUM/S] Voting panel is COMPARE_LLMS only: a PRIMARY_LLM outside COMPARE_LLMS is preflighted and paid for but its vote is silently discarded
**Evidence:** process_coin_with_comparison builds the panel exclusively from COMPARE_LLMS (crypto_trading_bot.py:1244-1247) and tallies the primary only `if llm == PRIMARY_LLM` inside that loop (1265-1268), so with e.g. --primary-llm=openai --compare-llms=gemini,claude the openai Round-1 analysis (always fetched, crypto_trading_bot.py:2400) is resolved into primary_rec (1199) and then dropped — it is neither counted nor cross-fed in integrate mode (r1_responses only fills from panel members, 1265-1272). Meanwhile get_active_llm_panel used by preflight DOES include the primary (crypto_trading_bot.py:1872-1877), so live mode hard-exits if the primary fails preflight (1932-1940) even though its vote can never count.

**Impact:** Config trap: the operator's mental model (and the preflight gate) says the primary is on the panel; the consensus math disagrees. Money is spent on an analysis that cannot influence the decision, and a 'consensus' can form without the model the operator designated primary. Not fail-open (quorum is still all of COMPARE_LLMS), but the panel the user configured is not the panel that votes.

**Recommendation:** Make the panel construction match get_active_llm_panel: build panel = dedupe([PRIMARY_LLM] + COMPARE_LLMS) in process_coin_with_comparison (crypto_trading_bot.py:1244-1247), or refuse/loudly warn at startup when PRIMARY_LLM not in COMPARE_LLMS in compare/integrate mode. Update tests/test_consensus.py accordingly.

### [MEDIUM/M] Whatif systematically diverges from live in three optimistic directions: no spread/fees in simulated fills, no daily cap, exclusion list not enforced
**Evidence:** (a) Simulated fills price at _current_ask, but the comment admits the Coinbase Product exposes no ask, so it lands on mid_market_price or last price (crypto_trading_bot.py:1513-1527) and records fees_usd=None (1572-1575) — live fills pay ~1.2%/side plus half-spread on meme-coin books. The analyzer applies the assumed 2.4% fee floor to whatif records too (tradeanalyzer.py:590-598), which covers fees but not spread/slippage. (b) The daily cap is checked only when `not WHATIF_MODE` (crypto_trading_bot.py:1639) and whatif intents don't count toward it, so a whatif day can 'execute' buys a live day would refuse — the whatif stream is not cap-censored the way live is. (c) The exclusion list is live-only (`if not WHATIF_MODE and coin_symbol in coinsToExclude`, crypto_trading_bot.py:1654), so whatif simulates buys of coins live mode will never place.

**Impact:** The whatif record — explicitly the analyzer's data engine per docs/RUNBOOK_whatif_cadence.md — overstates achievable live performance (spread on thin meme pairs can exceed the entire 2.4% fee floor) and contains trades (cap-excess, excluded coins) that live could not have made, so live-vs-whatif comparisons are biased in whatif's favor.

**Recommendation:** Minimum viable parity: (1) simulate the daily cap in whatif using the whatif intent rows (same summation, trading_mode='whatif'); (2) apply coinsToExclude in both modes; (3) record an estimated fee (notional * 1.2%) on simulated fill rows, or at least have the analyzer add a configurable spread haircut for whatif records so the two streams are graded on comparable costs.

### [MEDIUM/S] record_recommendation silently drops decisions (including blocked panel decisions) when the price fetch fails, contradicting the 'always recorded' contract; stored bid/ask are just the last price
**Evidence:** historyutil.record_recommendation returns None with only a console line when get_product_details fails or raises (historyutil.py:284-289), yet the call sites' comments promise 'Multi-LLM decisions are ALWAYS recorded — blocked ones as action NONE' (crypto_trading_bot.py:2418-2421). An LLM-discovered ticker that isn't listed on Coinbase (discovery validates only symbol shape, crypto_trading_bot.py:460-471) fails this fetch every time, so exactly the runs where discovery misbehaved leave no history. Also bid_price/ask_price fall back to price because the Product object has no bid/ask attributes (historyutil.py:236-240, corroborated by the _current_ask comment at crypto_trading_bot.py:1515-1517), so those record fields are permanently equal to price — dishonest data labeled as bid/ask.

**Impact:** Panel-behavior measurement (the entire point of recording blocked decisions) has a silent hole correlated with the most interesting failure cases, and downstream consumers of bid/ask (spread analysis) would be misled by fabricated equality.

**Recommendation:** Decouple recording from the price fetch: on fetch failure, still write the record with price/bid/ask = None (analyzer already maps missing rec_price to EXPIRED_UNSCORABLE, tradeanalyzer.py:558-559); store bid/ask as None rather than copying price when the attributes are absent.

### [MEDIUM/L] BUY-only execution: consensus SELL does nothing, no exit/stop path exists, and manual exits permanently desync attributed positions (already-documented, consequences under-stated)
**Evidence:** AGENTS.md:84 documents 'the execution ledger records only BUY fills today'. Verified: market_order_sell has zero callers ('nothing calls this yet', coinbaseutil2.py:485-491; grep confirms), coinsToSell is initialized and never appended (crypto_trading_bot.py:2011), and a unanimous SELL decision only writes a history record — the trade gate at 2450/2584 fires solely on 'BUY' in final_action. The daily cap bounds buys only (executionledger.py:324-341), so net exposure grows without bound ($15/day default = ~$450/month of un-exited positions); the analyzer's round-trip fee is a 2x-entry guess (tradeanalyzer.py:293-294); manual sells never enter the ledger so positions_from_rows drifts from account truth until someone manually runs scripts/reconcile_positions.py.

**Impact:** The system can enter but never exit: SELL consensus signals from the panel are collected and discarded, losses cannot be cut by the bot, and per-user attributed positions become fiction over time. At $5 scale this is tolerable, but it is the single largest gap between what the consensus machinery decides and what the money path can do.

**Recommendation:** Already-documented as accepted; when the SELL path lands, gate it on the same fail-closed decision machinery, record SELL intents/fills in the ledger (positions_from_rows already handles side='SELL', executionledger.py:258-262), and until then print a loud '[NO SELL PATH] consensus SELL recorded but not executable' line at the trade-gate call sites so operators see the dropped signal in run output.

### [MEDIUM/S] Analyzer candle cache keyed (coin, granularity) ignores the lookback span; out-of-window records silently grade against the nearest edge candle labeled AT_MATURITY
**Evidence:** CoinbasePriceProvider.price_at computes `days` from the FIRST record that misses the cache, then caches rows under cache_key=(coin, granularity) (tradeanalyzer.py:371-380); a later record for the same coin whose maturity_time predates the cached window reuses those rows, and `closest = min(rows, key=lambda r: abs(r['time'] - target))` (384-385) has no maximum-distance guard, so it returns the oldest candle in the window — possibly days from the target — while score_record still stamps methodology=AT_MATURITY (tradeanalyzer.py:564-567).

**Impact:** Records are graded against prices from the wrong time with the report explicitly claiming at-maturity methodology (the F4 flag exists precisely to prevent silent mixing), and the wrong grade is then frozen by the sidecar state.

**Recommendation:** Include the computed days in the cache key, and after selecting `closest`, return None when abs(r['time'] - target) exceeds ~1.5x the granularity's seconds (GRANULARITY_SECONDS is importable from marketdata) so the caller degrades to AT_RUN_TIME or EXPIRED_UNSCORABLE honestly.

### [LOW/S] Daily-cap refusals are absent from the run-summary tally (already-documented, still open)
**Evidence:** A [DAILY CAP] refusal returns before spend_tracker.try_spend is consulted (crypto_trading_bot.py:1639-1644), and the summary prints only spend_tracker.blocked as 'Blocked by spend cap' (crypto_trading_bot.py:2618). docs/ACCEPTANCE_RESULTS_2026-07-19.md issue 2 recorded exactly this ('the LINK refusal printed [DAILY CAP] but the summary showed 0'); the code is unchanged.

**Impact:** The summary is misleading in precisely the runs where the daily cap fired — an operator reading 'Blocked by spend cap: 0' may conclude nothing was refused.

**Recommendation:** Add a daily_cap_blocked counter incremented in the [DAILY CAP] branch of maybe_execute_buy and print it as its own summary line next to the run-cap tally.

### [LOW/S] Run-cap budget is consumed by excluded coins before the exclusion check, and the excluded coin still appears in coinsToBuy
**Evidence:** maybe_execute_buy commits the notional to spend_tracker (crypto_trading_bot.py:1647-1651) and appends to coinsToBuy (1653) BEFORE the coinsToExclude check returns without placing an order (1654-1658), so a live run that gates a BUY on an excluded coin (currently {'TRUMP'}, crypto_trading_bot.py:2238) burns $5 of run-cap headroom with no order and reports the coin under 'Coins to buy'.

**Impact:** Conservative direction (blocks more, never less), but a later legitimate BUY in the same run can be refused by [SPEND CAP] because budget was spent on a coin that was never buyable, and the summary claims a buy that did not happen.

**Recommendation:** Move the coinsToExclude check above both cap checks in maybe_execute_buy, and track excluded coins in their own list for the summary rather than coinsToBuy.

### [INFO/S] Quorum floor is an absolute 2 regardless of panel size; with REQUIRE_CONSENSUS=false, N-2 abstains still permit a 'unanimous' trade (documented/spec'd policy — recorded for design awareness)
**Evidence:** decide() blocks only when len(votes) < 2 (crypto_trading_bot.py:1307-1308); abstains are excluded from agreement math and block only under REQUIRE_CONSENSUS (1311-1313). tests/test_consensus.py:369 (test_abstain_excluded_from_agreement_without_require_consensus) pins this deliberately. Consequence: a 5-model panel run with REQUIRE_CONSENSUS=false trades on 2 surviving voters — which can be exactly grok+perplexity, the two providers still on the fallback delimiter parser (crypto_trading_bot.py:966).

**Impact:** Within stated policy (REQUIRE_CONSENSUS defaults true), but the AGENTS.md invariant phrasing ('never shrink the quorum') is stronger than the REQUIRE_CONSENSUS=false behavior actually delivers; an operator who disables consensus may not realize the effective quorum floor is 2, independent of panel size.

**Recommendation:** No code change required; consider a proportional floor (e.g. ceil(len(panel)/2)) or an explicit startup notice when REQUIRE_CONSENSUS=false states 'minimum 2 of N voters can trade', and align the AGENTS.md invariant wording with the spec'd REQUIRE_CONSENSUS=false semantics.
