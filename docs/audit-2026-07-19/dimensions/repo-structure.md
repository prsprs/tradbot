# Repository directory & file structure

## Summary
Structural cost is real but mostly navigational, with one cluster of findings that is genuinely load-bearing: pytest's test-discovery boundary is enforced only by convention (typing `pytest tests/ -q`), not configuration, and AGENTS.md itself contradicts that convention in its own commit procedure (line 32 says bare `pytest`, line 55 says `pytest tests/ -q`). Root-level clutter (37 .md files, 3 test-named manual probe scripts, 4 requirements files) is a real onboarding tax but low-risk to fix since nothing imports .md files and the probe scripts have zero importers. The one genuinely confusing code-structure issue is a naming collision between `historyutil.py` (the live bot's real history writer) and the `history/` package (the unrelated parallel llm_compare.py tool's history writer), compounded by a matching gitignore gap that let real recommendation data get committed under `history/`. None of this requires the kind of sweeping refactor AGENTS.md already (correctly) discourages for crypto_trading_bot.py — the concrete fixes below are all incremental, git-mv-shaped, and independently shippable.

## Strengths
- venv/, __pycache__/, and .pytest_cache/ are all correctly gitignored and confirmed untracked (`git ls-files venv/` returns 0 entries; `git check-ignore -v` confirms .gitignore coverage for venv/bin/python, .pytest_cache/README.md) despite being present in the working tree.
- The live_trades/ tracking problem the .gitignore's own comment (.gitignore:64-67) describes ("5 files already tracked... still need git rm --cached") has already been resolved — `git ls-files live_trades/` returns zero tracked files today; only the comment is now stale (see finding on .gitignore hygiene).
- The 4 requirements*.txt files are not actually in conflict: overlapping pins (pandas>=1.3.0, requests>=2.25.0, google-genai/anthropic/openai>=1.0.0) agree everywhere they repeat, and each file's header comment points at the others (requirements.txt:1-6) — the split-by-feature approach itself is a reasonable pattern, just missing a dev-tools file (see finding below).
- README.md already curates ~26 of the root feature docs into an implemented/design-only status table with working relative links (README.md:123-147) — a maintained index already exists, so a docs/ reorg only has to move files and fix that table's links, not invent curation from scratch.
- historyutil.py and executionledger.py already parameterize their data directory via a `HISTORY_DIR` env var with a `./history/` default (historyutil.py:15, executionledger.py:52) rather than hardcoding the path — this is exactly the mechanism AGENTS.md's hard rule #2 (what-if runs must set HISTORY_DIR) depends on, and it already exists cleanly for the main runtime path.

## Findings

### [HIGH/S] AGENTS.md's own commit procedure prescribes bare `pytest`, which is empirically broken and unsafe (contradicts the correctly-scoped `pytest tests/ -q` elsewhere in the same file)
**Evidence:** AGENTS.md:32 ("Bracket with the suite: full `pytest` green before the first commit and after the last") directly contradicts AGENTS.md:55 (`./venv/bin/python -m pytest tests/ -q`). Running bare `./venv/bin/python -m pytest --collect-only -q` from repo root empirically: (1) aborts the entire run — "Interrupted: 2 errors during collection", exit code 2 — because it also collects lab/session_tests_20260718/test_consensus.py:57 and test_extract_rec.py:43, which raise NameError (FAILED_INIT_LLMS / extract_tagged_vote undefined — these are exec()-into-namespace snippets, not real standalone tests); (2) silently imports root-level test_coinbase.py, which has no `if __name__` guard anywhere in the file and executes real top-level code including an authenticated `client.get_accounts()` Coinbase call merely by being collected; (3) collects test_trustwallet_swap.py:267 `def test_with_private_key():` and :593 `def test_sell_with_private_key():` as real pytest items (confirmed via `pytest --collect-only` output listing both node IDs) — these read a private key (env var or getpass) and reach toward a real Jupiter swap-and-confirm flow. None of this is protected by tests/conftest.py's network-blocking autouse fixture (tests/conftest.py:81-93), because that fixture is scoped only to tests collected under tests/ — its own module docstring (tests/conftest.py:30-34) explicitly acknowledges root-level 'probe before you migrate' scripts exist outside its coverage.

**Impact:** An agent following AGENTS.md's own commit checklist literally — or any agent that reflexively types `pytest` instead of the documented `pytest tests/ -q` — gets a crashed/interrupted verify step, a real (if read-only) Coinbase API call fired as a side effect of merely running "the test suite," and two collected test items that sit one interactive-input away from live wallet operations. The only thing currently preventing test_with_private_key/test_sell_with_private_key from progressing toward a real swap under pytest is that `input()`/`getpass()` error out under pytest's default stdout/stdin capture — an incidental protection, not a designed one, and it's void the moment `-s` is passed.

**Recommendation:** Add a `pytest.ini` (or `[tool.pytest.ini_options]` in a new pyproject.toml) at repo root with `testpaths = tests` and `norecursedirs = lab scripts venv .git` — explicit path args (as in the documented `pytest tests/ -q`) always override testpaths, so this is zero-risk to the existing verified workflow and makes bare `pytest` safe unconditionally. Additionally move+rename the three root probe scripts into `scripts/manual_probes/` as `probe_coinbase_accounts.py`, `probe_jupiter_swap.py`, `probe_trustwallet_swap.py` (0 importers found repo-wide, so this is a pure rename with no import fallout) and rename lab/session_tests_20260718/test_consensus.py and test_extract_rec.py off the `test_` prefix (e.g. `_consensus_snippet.py`) since they're historical session artifacts, not tests. Finally, fix AGENTS.md:32 to read `pytest tests/ -q` so the doc stops contradicting itself.

### [HIGH/S] history/ gitignore coverage has a real gap: history/llm_compare_history.json is tracked in git and contains real accumulated recommendation data, contradicting AGENTS.md's explicit claim that "the gitignore enforces" per-user-data exclusion under history/
**Evidence:** .gitignore:37-43 enumerates history/recommendations.json, history/executions.json, history/analyzer_state.json, and history/*.csv (with an explicit exception for the documented fixture test_expected_output.csv) but never mentions llm_compare_history.json. `git ls-files history/` lists history/llm_compare_history.json as tracked; its content (verified via `./venv/bin/python -c "import json; print(json.load(open('history/llm_compare_history.json')).keys())"`) is `{"recommendations": [...]}` with 12 real records each carrying id/timestamp/prompt/prompt_hash/round_1_responses/round_2_responses/final_recommendation/summary — the same shape/class of data as the gitignored history/recommendations.json. It was added once (git log: commit ca355e2, 2026-04-24) and has sat tracked ever since. history/recorder.py:13 is what writes it (`history_file: str = "./history/llm_compare_history.json"`, used by llm_compare.py:16's HistoryRecorder), with no HISTORY_DIR-style env override the way historyutil.py:15 and executionledger.py:52 have for the main bot.

**Impact:** Real recommendation history (prompts, LLM responses, timestamps) from running the parallel llm_compare.py tool has been committed and stays in git history, directly contradicting AGENTS.md hard rule #3 ("Never commit per-user data ... The .gitignore enforces this"). The enumerate-by-filename gitignore strategy is proven not self-maintaining: any new data file the parallel stack starts writing needs its own manually-added line or it silently gets swept into the next `git add`.

**Recommendation:** Add `history/llm_compare_history.json` to .gitignore immediately (owner decides separately whether to purge it from history). Structurally, stop enumerating data files by name: keep `history/` as pure code (recorder.py, __init__.py, test fixtures) and move the *default* write location for both historyutil.HISTORY_DIR and HistoryRecorder's default path to a sibling directory (e.g. `var/`) that is wholesale-gitignored with one line (`var/`). historyutil.py:15 and executionledger.py:52 already support this via the HISTORY_DIR env var, so only the default constant needs to change; history/recorder.py:13's default is a separate hardcoded string and would need the same env-override pattern added for parity.

### [HIGH/S] Naming collision between the money-path's history module (historyutil.py) and the unrelated history/ package — a real confusion risk, not yet documented in AGENTS.md
**Evidence:** crypto_trading_bot.py:31 imports `from historyutil import record_recommendation` — the flat file at repo root that persists real bot recommendations to history/recommendations.json (historyutil.py:1-16). Separately, llm_compare.py:16 imports `from history.recorder import HistoryRecorder` — the `history/` package, which is unrelated to the live bot and writes to history/llm_compare_history.json (history/recorder.py:13-14). Two independently-named, functionally unrelated "history" subsystems — one flat module one letter different from a package directory of almost the same name — sit in the same top-level listing. AGENTS.md:24 documents that `history/` mixes tracked code (recorder.py) with gitignored data, but never mentions that historyutil.py (a completely separate module) is what the live bot actually uses.

**Impact:** An agent asked to fix or extend "history recording" for the live bot has a real chance of opening history/recorder.py first (it's the directory; it sounds authoritative) and reasoning about or patching the wrong subsystem — exactly the class of mistake AGENTS.md's own process lesson at line 106 ("verify spec claims against the code") warns about, one level up: at file-identification time rather than spec-compliance time.

**Recommendation:** Cheapest fix (do now): add a one-line docstring cross-reference at the top of each file ("if you're looking for the live bot's history writer, see historyutil.py at repo root, not this package" / vice versa). Longer-term (separate, larger change): rename historyutil.py to something unambiguous (e.g. bot_history.py) — it has exactly 3 importers repo-wide (grep-verified), so the rename is a small, bounded, single-commit change; alternatively rename the history/ package (used only by the llm_compare stack) to something like llm_compare_history/ to match the naming pattern of its sibling packages (llm_utils/, prompts/, context/), which are already scoped to that stack by name.

### [MEDIUM/M] ~36 feature/plan/manual .md files (1.5MB total) sit flat at repo root with no directory grouping — concrete target layout proposed
**Evidence:** `ls *.md | wc -l` = 37 tracked root .md files (36 feature/plan/manual docs plus AGENTS.md/CLAUDE.md/README.md/README_LLM_COMPARE.md/MODELS.md as the core set). `du -sh *.md` totals ~1.5M; 'Restore Directional Analysis.md' alone is 408K/10,197 lines and is a raw exported IDE chat transcript (confirmed by its header: "# Cascade Chat Conversation" / "### User Input" / "### Planner Response" — a Windsurf session log, not authored documentation), the only root .md with spaces/mixed-case naming and not referenced anywhere in README.md's feature index. README.md:123-147 already curates ~26 of the remaining files into an Implemented/Design-Only status table with working relative links, so a maintained index already exists.

**Impact:** Pure navigability cost, no correctness risk: `ls` at repo root surfaces 37 markdown files before a newcomer reaches any .py source (87 total top-level entries via `ls -1 | wc -l`), any repo-wide grep for a keyword picks up design-doc prose alongside real source, and an AI agent's orientation pass pays a large read-and-triage tax.

**Recommendation:** Single target layout, staged as pure `git mv` (nothing imports .md files, so zero import-breakage risk — only the handful of relative links need fixing in the same commit): Stage A — create docs/features/ and move all *_FEATURE.md + LLMCompareFeature.md + CRYPTO_TRADING_BOT.md + README_LLM_COMPARE.md there. Stage B — create docs/manuals/ and move all *_OPERATIONS_MANUAL.md + OPERATIONS_MANUAL.md there. Stage C — create docs/archive/ for mechanically-flagged stale-plan candidates (staleness judgment itself is a sibling reviewer's job, but a cheap first-pass filter is: not linked from README.md's feature table AND untouched since its initial commit — by that rule 'Restore Directional Analysis.md', METHODS_OF_SPECIFYING_RUNTIME_OPTIONS.md, PARSING_OPTIONS_FOR_VARIABLE_INPUT.md, INSTRUCTIONS_FOR_IMPLEMENTATION.md, and LIVE_MODE_PREFLIGHT_IMPLEMENTATION_PLAN.md are candidates; EVALUATION_LESSONS_LEARNED_2026-07-18.md is explicitly NOT a candidate since AGENTS.md:78 actively cites it as canonical). Stage D — leave AGENTS.md, CLAUDE.md, README.md, and MODELS.md at root (MODELS.md is named directly in AGENTS.md hard rule #5 and the architecture map). Each stage: `grep -n '\.md\]' README.md AGENTS.md OPERATIONS_MANUAL.md CRYPTO_TRADING_BOT.md` first to enumerate every cross-reference, move the files, then fix every match in the same commit.

### [MEDIUM/L] No coherent package story for ~29 flat top-level .py modules vs. the 5 real packages — the existing packages all belong to one stack (llm_compare.py) by historical accident, not by design
**Evidence:** context/__init__.py:1, prompts/__init__.py:1, llm_utils/__init__.py:1, and history/__init__.py:1 all literally say "...for the multi-LLM advisory system" (i.e. llm_compare.py's stack, per AGENTS.md:76). dex/ is the only other real package (Solana-specific). Meanwhile the live-money runtime path and its direct dependents (marketdata.py, coinbaseutil2.py, historyutil.py, executionledger.py, voteschema.py, modelregistry.py, claudeutil.py, openaiutil.py, grokutil.py, perplexityutil.py), a family of large standalone analysis tools (correlation_tracker.py 128K/2900 lines, leading_indicator_tester.py 244K/5644 lines, fibonacci_analyzer.py 48K, lp_analyzer.py/lp_arbitrage.py/lp_history.py, tradeanalyzer.py), and generic data-provider clients (coingeckoutil.py, coinmarketcaputil.py, lunarcrushutil.py, santimentutil.py, polymarketutil.py) all sit flat at root. Import-count check (grep-based) shows real cross-file coupling that any regrouping must respect: modelregistry (11 importers), voteschema (9), correlation_tracker/marketdata (5 each), vs. candidate_util.py (0 importers), lunarcrushutil.py/santimentutil.py/polymarketutil.py (1 each). Note: AGENTS.md:99 already documents crypto_trading_bot.py itself as "the standing refactor candidate" for splitting — that specific point is already-known; the broader observation that the same one-big-flat-file pattern exists for correlation_tracker.py/leading_indicator_tester.py/fibonacci_analyzer.py, and that there's no grouping convention at all for the smaller flat modules, is not covered by that existing note.

**Impact:** Purely an onboarding/navigability cost today (no functional bug) — but AGENTS.md's own process lesson (line 99) warns that crypto_trading_bot.py-adjacent work is easy to conflict on precisely because it's one big flat file with no module boundaries; the same risk quietly extends to the other giant flat analysis modules that aren't called out.

**Recommendation:** Treat as an explicit phase-2/optional target, not urgent — rushing a repo-wide import-line regrouping is exactly the kind of parallel-edit hazard AGENTS.md already cautions against. Proposed target packages: `bot/` (money-path dependents), `providers/` (coingeckoutil/coinmarketcaputil/lunarcrushutil/santimentutil/polymarketutil), `analytics/` (correlation_tracker/fibonacci_analyzer/leading_indicator_tester/lp_*/tradeanalyzer/candidate_util). Migrate one module at a time using an old-path shim so nothing breaks mid-migration: `git mv coingeckoutil.py providers/coingeckoutil.py`, then leave `# back-compat shim, remove once all imports updated\nfrom providers.coingeckoutil import *` at the old path; update the (few) real importers in a follow-up commit; delete the shim last. Start with the 0-importer / 1-importer modules (candidate_util.py, lunarcrushutil.py, santimentutil.py, polymarketutil.py) to prove the pattern cheaply before touching modelregistry.py or voteschema.py, which are used everywhere and should stay untouched until the pattern is validated.
