# Logging prowess and readability

## Summary
The consensus/vote/trade-gate decision path is unusually well self-documented for an MVP: a consistent, greppable bracket-tag vocabulary ([BLOCKED], [ABSTAIN], [COMPARISON]/[INTEGRATE], [TIEBREAKER], [STRUCTURED VOTE], [FALLBACK PARSER], [LEDGER], [ORDER], [DAILY CAP], [SPEND CAP], [LIVE LOCK]) prints the vote-by-vote breakdown and block_reason at the exact point of decision, and trading_mode is loudly restated at run start (both a downgrade-notice banner and a plain banner line) and again in the end-of-run summary. However, the runtime path (crypto_trading_bot.py, coinbaseutil2.py, executionledger.py, voteschema.py, marketdata.py) uses zero `logging`-module calls -- it is 100% ad hoc print(), with no per-line timestamps, no persisted/rotated log file (stdout-only; the RUNBOOK's own cron examples append forever to one unbounded file), and no use of `traceback`/`logging.exception` anywhere despite 18+ bare `except Exception as e: print(...)` blocks on the consensus/order path. Two adjacent non-money-path files (correlation_tracker.py, leading_indicator_tester.py) already establish a working `logging.basicConfig(format='%(asctime)s [%(levelname)s] %(message)s')` pattern the runtime path could adopt cheaply. The most consequential gaps are a fail-open daily-spend-cap path whose ledger-read failure is logged as a bare, untagged "Warning: ..." line (invisible to anyone grepping the established tag vocabulary), and an unconditional, untagged full-text dump of every primary LLM response that bypasses an already-existing verbosity flag.

## Strengths
- crypto_trading_bot.py's tally path (process_coin_with_comparison, ~lines 1277-1402) prints the full per-panelist vote/abstain breakdown (votes_display) then [ABSTAIN]/[BLOCKED]/[TIEBREAKER]/[COMPARISON]/[INTEGRATE] tags at the exact decision point, with block_reason spelled out in plain English (e.g. 'sub_quorum: only 1 of 3 panelist(s) produced a vote', line 1308) -- a human or agent can reconstruct exactly why a trade did or didn't happen from stdout alone.
- voteschema.resolve_structured_vote (voteschema.py:349-387) and the delimiter fallback (crypto_trading_bot.py:969-1016) both use the same '[STRUCTURED VOTE]'/'[FALLBACK PARSER]' prefix convention and log every terminal outcome (empty response, schema violation, explicit abstain, symbol mismatch, success) -- consistent and complete coverage of the parse-to-vote path.
- The live/whatif double-lock is unmissable: a downgrade prints a '!'-banner-wrapped multi-line '[LIVE LOCK]' notice (crypto_trading_bot.py:2030-2034) and the resolved mode is restated in a plain startup banner ('Trading Mode: LIVE/WHAT-IF', line 2282-2287) and again in the end-of-run summary (line 2592).
- Money-path facts (trading_mode, run_id, action, order_id, fills, block_reason) are durably persisted to JSON via historyutil/executionledger, not just printed -- so the decision itself survives even if stdout/log output is lost; only the qualitative LLM reasoning text is stdout-ephemeral.
- marketdata.py's secondary-data fetch failures ([CMC]/[LUNARCRUSH]/[MARKET DATA], lines 434/474/657) degrade quietly and correctly with a one-line reason each, avoiding per-candle/per-fetch spam while still being traceable on failure.

## Findings

### [HIGH/S] Execution-ledger read failure fails open on the daily live-spend cap and is logged with an untagged, ungreppable line
**Evidence:** executionledger.py:79-89 `load_executions()` catches `(json.JSONDecodeError, IOError)` and does `print(f"Warning: Could not load execution ledger: {e}")` then `return []` -- no bracket tag, unlike every other warning in the codebase ('[WARNING]', '[CONFIG WARNING]', '[DAILY CAP]', '[LEDGER]'). `live_spend_today()` (executionledger.py:353-361) and `daily_cap_would_exceed()` (line 364+) both flow through `load_executions()` with no other guard, so an empty list is indistinguishable from 'no spend today yet'.

**Impact:** If executions.json is ever corrupted or transiently unreadable (plausible: multiple users each run their own instance per AGENTS.md, and this is the one file written on every buy), the daily live-spend cap silently resets to $0 for that call -- the opposite of the repo's own stated invariant 'fail closed on the money path... never shrink the quorum' (AGENTS.md line 101), except here it's the spend cap, not the quorum. Worse for this audit's dimension: because the warning doesn't use the established tag vocabulary, an agent or human scripting a log monitor around '[WARNING]'/'[ERROR]'/'[DAILY CAP]' -- the exact tags this codebase trained them to grep for -- will never see it fire.

**Recommendation:** Tag the line consistently, e.g. `print(f"[LEDGER ERROR] executions.json unreadable ({e}); daily spend cap check may under-count today's live spend -- treating as 0, DO NOT rely on cap enforcement until this is fixed")`, and consider making `daily_cap_would_exceed` fail closed (return True / refuse the buy) rather than fail open when `load_executions()` errors, since a cap check that can't read its own data has no basis to say 'under cap'.

### [MEDIUM/S] Full raw LLM response text is dumped unconditionally and untagged for every primary-LLM call, bypassing the codebase's own verbosity flag
**Evidence:** crypto_trading_bot.py:2402 and :2537 both do `print(followUpResponseText)` unconditionally (once per coin, per run, at both the discovery-loop and user-specified-coins call sites) immediately before the `[PRIMARY]` char-count line. Contrast crypto_trading_bot.py:1273-1275, where the equivalent dump for non-primary panelists is explicitly gated: `if resp and LOG_INTEGRATION_ROUNDS: print(...); print(resp)`.

**Impact:** Every scheduled what-if run (the RUNBOOK's cadence is 4x/day, 4 coins, appended forever to one log file per docs/RUNBOOK_whatif_cadence.md) unconditionally interleaves multi-hundred-to-few-thousand-character raw LLM text with no tag prefix between the terse, well-tagged control-flow lines, defeating grep-based triage and inflating the one artifact (the log file) that already has no rotation strategy. The existing `LOG_INTEGRATION_ROUNDS` flag shows the intent to gate exactly this kind of dump was already understood elsewhere in the same function family, just not applied here.

**Recommendation:** Gate `print(followUpResponseText)` at both call sites behind `LOG_INTEGRATION_ROUNDS` (or a new `--verbose`/`LOG_RAW_RESPONSES` flag) the same way the peer-panelist dump already is, and keep the always-on `[PRIMARY] ... {n} chars` line as the default signal.

### [MEDIUM/S] Bare `except Exception as e: print(...)` on the core consensus/API path discards the traceback everywhere
**Evidence:** crypto_trading_bot.py has 18 `except Exception as e:` blocks; none use `traceback` (confirmed: `grep -n traceback` across all 5 audited files returns zero hits). Two on the money/consensus path: get_llm_response's API-call wrapper (line 951-953, `print(f"Error getting {llm_name} response: {e}")`) and the multi-LLM block's outer guard (line 1396-1402, `print(f"Error in LLM processing for {coin_symbol}: {e}")` then `[BLOCKED]`) -- both correctly fail closed per T3(f), but only the exception's string repr survives in the log, never a stack trace or originating line.

**Impact:** The fail-closed *behavior* is correct (a genuine strength), but when the exception is an actual bug rather than an anticipated provider hiccup, an unattended cron run's only diagnostic artifact is `str(e)` with no file/line context -- materially slowing root-cause for whoever (human or agent) reads the log later, which matters more here than usual since the repo is explicitly maintained by AI agents working from transcripts/logs rather than live debugging sessions.

**Recommendation:** Replace the bare `print(f"...{e}")` in these handlers with `print(f"...{e}"); import traceback; traceback.print_exc()` (or adopt `logging.exception(...)`, which includes the traceback automatically) at minimum on the two consensus-path handlers (crypto_trading_bot.py:951-953, 1396-1402); a repo-wide sweep of all 18 is a good follow-up but not required to capture most of the value.

### [MEDIUM/M] No persisted/rotated log file and no per-line timestamps on the runtime path; a local `logging.basicConfig` pattern already exists two files away and isn't reused
**Evidence:** `grep -c logging` across crypto_trading_bot.py, coinbaseutil2.py, executionledger.py, voteschema.py, marketdata.py is 0 for all five (verified via `import logging` count = 0 in each). docs/RUNBOOK_whatif_cadence.md's own cron/launchd examples pipe stdout as `>> "$HOME/tradbot_whatif.log" 2>&1` with no rotation, and no code path adds a wall-clock timestamp to any print line -- the only timestamp in the entire run's stdout is the one-time `Run ID: run_YYYYMMDDTHHMMSSZ` banner (crypto_trading_bot.py:2290). By contrast, correlation_tracker.py:36-43 and leading_indicator_tester.py already do `logging.basicConfig(level=logging.INFO, format='%(asctime)s [%(levelname)s] %(message)s')` plus `logger = logging.getLogger(__name__)`, a working pattern in the same repo the runtime path never adopted.

**Impact:** For a bot designed to run unattended on a 6-hour cron cadence indefinitely (per the RUNBOOK), a single ever-growing, timestamp-sparse log file makes 'what happened around 2026-08-15 14:00' a manual scan for the nearest `Run ID:` line rather than a timestamp grep, and gives no rotation/size-bound story at all for a process meant to run for months.

**Recommendation:** Add a minimal, low-risk wrapper: either switch to `logging.basicConfig(format='%(asctime)s %(message)s')` with the existing print-string bodies passed to `logger.info`/`logger.warning`/`logger.error` (mechanical find/replace, preserves all existing bracket tags), or at minimum prefix every print with a shared `_ts()` helper. Pair with a RUNBOOK update recommending per-run log files (e.g. `logs/whatif_${RUN_ID}.log` via a wrapper script) or `logrotate`/`newsyslog` for the single-file cron examples already documented.

### [LOW/S] Inconsistent [ORDER] tag coverage on coinbaseutil2.py's own top-level exception prints
**Evidence:** coinbaseutil2.py:229 `print(f"Error placing market buy order for {product_id}: {e}")` and line 501 `print(f"Error placing market sell order for {product_id}: {e}")` have no tag, while every downstream line in the same failure-recovery path is tagged: line 279 `[ORDER] UNVERIFIED create failure...`, line 404 `[ORDER] client_order_id=...: lookup found no matching order...`, line 408 `[ORDER] Idempotent recovery: ...`. Lines 147 (`Error getting product details`), 175 (`Error fetching accounts`), and 565 (`Error listing products`) are similarly untagged.

**Impact:** A grep for the established `[ORDER]` tag -- the natural thing to script around, given how consistently it's used elsewhere in this same file -- misses the raw exception text of the actual create-call failure and only catches the recovery path's paraphrase, which can differ in wording from the original exception.

**Recommendation:** Prefix these five untagged error prints with `[ORDER]` (buy/sell placement) or a distinct `[COINBASE]` tag (account/product/list calls) to match the convention already used 12+ times elsewhere in the same file.

### [LOW/S] '[FALLBACK PARSER]' fires unconditionally on every grok/perplexity call, diluting its value as an anomaly signal
**Evidence:** crypto_trading_bot.py:991-993 prints `[FALLBACK PARSER] {llm_name}/{coin_symbol}: structured output not enabled for this provider; parsing delimiter tag` before any parsing is attempted, i.e. on every single call to grok or perplexity regardless of outcome -- not gated on failure. AGENTS.md line 75 and the code's own T8 comment (crypto_trading_bot.py:963) both describe this as 'a loudly-logged fallback' implying it should flag something notable.

**Impact:** Since grok/perplexity are always routed through this path by design (STRUCTURED_VOTE_PROVIDERS excludes them, line 966), the tag is really steady-state routing information, not an anomaly signal -- a reader expecting '[FALLBACK PARSER]' to mean 'something needed fallback handling' will instead see it on 100% of ordinary calls to those two providers, alongside the genuinely-anomalous sub-cases (parse failure, symbol mismatch) that already have their own distinguishable messages a few lines later (lines 1004-1015).

**Recommendation:** Low priority / optional: split into a quiet one-time-per-run routing note (or drop it, since STRUCTURED_VOTE_PROVIDERS already documents which providers use which path) and reserve '[FALLBACK PARSER]' language for the actual failure/success outcome lines that already exist (crypto_trading_bot.py:1004-1015), which are the ones worth grepping for.
