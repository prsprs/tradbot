# AI/LLM API interactions and model usage

## Summary
Model-ID centralization is genuinely clean (no hardcoded model IDs outside modelregistry.py) and the structured-vote path fails closed correctly, which are the two things that matter most for a real-money consensus bot. The main weaknesses are architectural: the panel-trader stack (*util.py) and the parallel llm_utils/ stack have drifted in a way that silently breaks the preflight's core guarantee for Claude; a fail-open legacy consensus helper is imported into the money-path module; there is no LLM-spend observability or budget ceiling on a bot that fires up to 10 provider calls per coin; and analysis prompts are copy-pasted verbatim across five call sites so adding a 6th provider is shotgun surgery. None of these can directly cause a wrong trade today, but two of them defeat safety/observability mechanisms the repo already invested in.

## Strengths
- Model-ID centralization is disciplined: a repo-wide grep for provider model strings (gpt-*/claude-*/gemini-*/grok-*/sonar) finds ZERO hardcoded IDs outside modelregistry.py — every hit is in a comment/docstring. All 14 call sites resolve through get_model(); modelregistry.get_model reads env overrides at call time and raises ValueError on an unknown provider (modelregistry.py:52-59).
- The structured-vote path fails closed by construction: voteschema.parse_vote is strict on every field and never raises (voteschema.py:219-288); resolve_structured_vote maps empty text→abstain('parse_failure'), abstain=true→abstain('refusal'), symbol-mismatch→abstain('symbol_mismatch'), and wraps everything in a defensive try/except (voteschema.py:349-388). Empty-text-at-cap can never become a consenting vote.
- Prompt-injection surface from market/social data is handled deliberately: marketdata.py:58-61 documents the risk and build_social_section (marketdata.py:661-695) only ever emits explicitly-extracted numeric/enum fields — free-text CMC/LunarCrush fields (tags, titles, related_topics) are never passed through into a prompt.
- Preflight gating is fail-closed in live mode: run_llm_preflight hard-exits on any provider failure in live, warns-and-continues only in whatif (crypto_trading_bot.py:1932-1945). F1 client_init_failure keeps a dead provider IN the panel as a standing abstain rather than silently shrinking quorum (crypto_trading_bot.py:1032-1054, 864-869).
- Gemini and Grok analysis calls are intentionally left uncapped on output tokens (gemini_structured_config crypto_trading_bot.py:503-507; grokutil _call_responses_api sends no max_output_tokens), correctly matching the documented reasoning-model empty-text-at-cap gotcha rather than risking abstains from a tight budget.
- reasons content-hygiene added after a live incident: _clean_reasons strips parse debris and parse_vote fails the whole payload closed when debris dominates the reasons array (voteschema.py:188-216, 283-285).

## Findings

### [HIGH/S] Preflight probes a different Claude client than the money path, so a green preflight does not guarantee the production trader constructs
**Evidence:** llmpreflight._probe_claude() constructs llm_utils.ClaudeClient() (llmpreflight.py:112-113), which reads `ANTHROPIC_API_KEY or CLAUDE_API_KEY` (llm_utils/claude_client.py:18). But the actual money-path panelist is claudeutil.ClaudeTrader (constructed in crypto_trading_bot.py:2177), which reads ONLY CLAUDE_API_KEY and raises otherwise (claudeutil.py:27-29). The llmpreflight module docstring explicitly claims 'a preflight pass is a real signal that the production code path works' (llmpreflight.py:12-16) — false for Claude. The inverse divergence exists for Gemini: preflight uses llm_utils.GeminiClient which requires GOOGLE_API_KEY (gemini_client.py:19-21), while the money path uses a bare genai.Client() (crypto_trading_bot.py:2167) that also accepts GEMINI_API_KEY.

**Impact:** If an operator sets only ANTHROPIC_API_KEY (the standard Anthropic variable name), the startup preflight reports Claude OK, live mode does NOT hard-exit, then ClaudeTrader() raises at construction → register_client_init_failure('claude') → standing abstain('client_init_failure') for the entire run → under REQUIRE_CONSENSUS every trade is blocked despite a green preflight. It fails closed (no bad trade) but wastes the full analysis cycle preflight exists to protect and gives contradictory operator signals (preflight says OK, run says client-init-failure).

**Recommendation:** Make claudeutil.ClaudeTrader read `os.environ.get('ANTHROPIC_API_KEY') or os.environ.get('CLAUDE_API_KEY')` so it matches llm_utils/claude_client.py exactly. Longer term, have llmpreflight probe the actual money-path classes (ClaudeTrader/OpenAITrader/GrokTrader/PerplexityTrader + the inline genai.Client construction) instead of the llm_utils/ clients, or collapse the two client stacks so preflight and production cannot diverge. Add a regression test asserting the preflight client and the trader agree on required env vars for every provider.

### [MEDIUM/S] Fail-open legacy consensus helpers are imported into the money-path module but never called
**Evidence:** crypto_trading_bot.py:23 imports `compare_recommendations, get_consensus_action` from claudeutil, but a repo-wide grep finds zero invocations of either (only the import and their definitions). get_consensus_action(comparison_result, require_consensus=False) returns `comparison_result['gemini']` — a single-model Gemini fallback — with the comment 'Default to Gemini if no consensus required' (claudeutil.py:243-245). compare_recommendations implements a 2-LLM-only Gemini-vs-Claude agreement check (claudeutil.py:194-224), entirely superseded by the hardened PanelDecision path.

**Impact:** This is dead code today, but it is a loaded gun in the money-path module: it encodes exactly the fail-OPEN single-model behavior the repo's core invariant forbids ('never fall back to a single model'), it is already imported into the main bot, and a future agent grepping for 'consensus' helpers could wire it back in. It also misleads readers into thinking two competing consensus implementations are both live.

**Recommendation:** Delete compare_recommendations and get_consensus_action from claudeutil.py and remove them from the crypto_trading_bot.py:23 import, or if kept for llm_compare-style use, move them out of the money-path module and add an assertion/comment that they must never gate a real trade. Confirm no test depends on them first (grep tests/).

### [MEDIUM/M] No LLM-spend observability or budget ceiling anywhere on the money path
**Evidence:** Grepping crypto_trading_bot.py + all four *util.py traders for usage/token/cost accounting returns nothing except the hardcoded `4096` caps (openaiutil.py:30,55,91,111,156). No call site reads response.usage / reasoning_tokens / thoughts_token_count, and none logs or accumulates cost, even though MODELS.md Appendix documents these fields per provider and warns Perplexity bills a per-request fee on top of tokens (MODELS.md:209-214). Gemini and Grok analysis calls are output-uncapped (crypto_trading_bot.py:503-507; grokutil.py:25-29). The only cost logic in the repo, config.estimate_cost, serves llm_compare.py only and uses stale flat rates `input*0.00001 + output*0.00003` (config.py:350) that ignore per-provider pricing and Perplexity's request fee. The RUN_SPEND_CAP_USD/DAILY_SPEND_CAP_USD trackers cover Coinbase trade notional, not API spend.

**Impact:** A bot that several users run repeatedly fires up to 5 providers × 2 rounds = 10 calls per coin with uncapped output on two of them, and nobody can see or cap the resulting API spend. A misconfigured loop, a reasoning-heavy model, or a runaway coin list can quietly run up real money with no signal and no ceiling.

**Recommendation:** Capture response.usage (OpenAI/Perplexity completion_tokens_details.reasoning_tokens, Gemini usage_metadata.thoughts_token_count, Claude usage.output_tokens, Grok usage.output_tokens_details, plus Perplexity's usage.cost) at each call site, log a per-coin and per-run token/cost tally, and add an optional per-run LLM-spend cap that aborts the panel loop when exceeded — mirroring the existing trade-notional caps. Update config.estimate_cost's rates or replace with per-provider figures.

### [MEDIUM/M] Analysis prompt text and coin-type framing are duplicated verbatim across five call sites; a 6th provider is shotgun surgery
**Evidence:** The coin-check / trend-check / integrated-check question wording is copy-pasted across claudeutil.py, openaiutil.py, grokutil.py, perplexityutil.py, and the inline Gemini functions in crypto_trading_bot.py (e.g. the identical 'Would a sophisticated trading bot designed for short-term appreciation recommend buying, selling, or holding...' string appears in claudeutil.py:73, openaiutil.py:60, grokutil.py:56, perplexityutil.py:53, crypto_trading_bot.py:520). The 'cryptocurrency' vs 'meme coin' framing is re-derived in each of the four traders' __init__ (claudeutil.py:33-34 etc.) plus separately in the bot's own functions. Adding a provider requires edits across ~8-10 sites: modelregistry DEFAULT_MODELS+ENV_OVERRIDE_VARS, a new *util.py trader (6 methods), a new llm_utils/*_client.py, llm_utils/__init__.py lazy import, llmpreflight._PROBES (+_SCHEMA_PROBES), the main() construction block (crypto_trading_bot.py:2174-2211), the get_llm_analysis if/elif dispatch (crypto_trading_bot.py:889-950), STRUCTURED_VOTE_PROVIDERS (crypto_trading_bot.py:966), and config.AVAILABLE_LLMS.

**Impact:** A change to the analysis question or the framing logic is a five-file edit that is easy to apply inconsistently, meaning different panelists could silently be asked subtly different questions — a correctness hazard for a consensus system. Onboarding a provider touches the money path in ~10 places, raising the chance of a fail-open gap slipping in. AGENTS.md documents the llm_utils-vs-util client duplication but not this separate prompt-text-across-traders duplication.

**Recommendation:** Extract the analysis prompt bodies and the coin-type framing into shared builders (e.g. in prompts/ or voteschema-adjacent) that every trader and the inline Gemini path call, so wording lives once. Then reduce the get_llm_analysis dispatch to a registry/dict of {provider: client} to shrink the per-provider surface. This does not require unifying the two client stacks in one step — the prompt text can be centralized independently.

### [MEDIUM/M] Delimiter-tag fallback parser is fragile precisely for the two web-search providers that append trailing prose
**Evidence:** grok and perplexity are the only providers on the delimiter fallback (crypto_trading_bot.py:966 STRUCTURED_VOTE_PROVIDERS excludes them). extract_tagged_vote enforces a concluding-tag rule: if ANY letter follows the last `<**SYM-PRS-ACTION**>` tag, it returns (None,None) → abstain (crypto_trading_bot.py:794-797). But grok and perplexity both run live web search and commonly append sources/citations/prose after their conclusion; perplexity in particular emits trailing reference text. MODELS.md:234-235,263-267 confirms structured JSON was probe-verified working for BOTH (fixtures exist) yet neither adopted it. AGENTS.md's F6 note admits the concluding-tag rule was measured on only 8 responses with zero rejections.

**Impact:** Systematic over-abstention risk for the two providers most likely to trail their answer with letters: each spurious abstain shrinks the panel and, under REQUIRE_CONSENSUS, blocks trades that a correct parse would have allowed. It fails closed (no wrong trade) but silently degrades the consensus the operator configured, and the 8-response sample is too small to trust in production. (Partially documented as known.)

**Recommendation:** Adopt native structured output for grok (Responses API text.format json_schema) and perplexity (response_format json_schema, no name/strict wrapper) using the already-captured fixtures in tests/fixtures/structured_output/, moving them into STRUCTURED_VOTE_PROVIDERS; or, as a smaller step, relax the concluding-tag rule for these two to tolerate a trailing sources/citations block. Either way add fixtures of real grok/perplexity responses that carry trailing prose and assert the vote still parses.

### [LOW/S] No explicit request timeouts on any LLM call; one hung provider can stall a run for minutes per coin
**Evidence:** None of the call sites set a timeout: claudeutil/openaiutil/grokutil/perplexityutil and llm_utils/*_client.py all call the SDK create() with no timeout argument, and the inline Gemini calls (crypto_trading_bot.py:484-489, 518-522, etc.) use a GenerateContentConfig with no timeout. They rely on SDK defaults (Anthropic/OpenAI default ~600s).

**Impact:** On a flaky provider, a single call can hang for up to ~10 minutes; across 5 providers × 2 rounds × N coins a stalled run could hang for a very long time before the upstream try/except (crypto_trading_bot.py:951) ever records the failure. Fails closed but hurts the loop's responsiveness for a bot meant to act on short-term signals.

**Recommendation:** Set an explicit per-call timeout (e.g. 60-90s) on each SDK client or request — anthropic/openai accept `timeout=`, google-genai accepts an http options timeout — so a hung provider becomes a fast abstain rather than a multi-minute stall.

### [INFO/S] Round-2 peer analysis injects raw peer-LLM text (carrying web-search/social content) into other models' prompts
**Evidence:** Round-2 builders embed the previous round's raw response text verbatim between `---BEGIN PEER ANALYSIS---`/`---END PEER ANALYSIS---` delimiters (claudeutil.py:136-138, openaiutil.py:120-122, grokutil.py:98-100, perplexityutil.py:111-113, crypto_trading_bot.py:577-579). That peer text can originate from grok/perplexity web search or LunarCrush-influenced reasoning, so untrusted external content can flow one model→another model's prompt.

**Impact:** Bounded, not currently exploitable into a trade: the final vote is schema-constrained and symbol-bound (voteschema.parse_vote + bind_symbol), so injected peer text can at most influence a model's reasoning, never directly forge a vote or a symbol. Worth tracking because market/social data injection elsewhere is deliberately sanitized (a genuine strength) while this cross-model channel is not.

**Recommendation:** No code change required for the current threat model; document this as an accepted, bounded surface next to the marketdata.py:58-61 injection note, and keep the schema/symbol binding as the backstop. If desired, cap peer_analysis length and strip control characters before embedding.
