# Programming best practices & code quality

## Summary
Judged as a small real-money MVP maintained by AI agents, the money path itself is in good shape: the consensus core (process_coin_with_comparison) is fail-closed, well-decomposed into nested helpers, and heavily docstring'd, and the Coinbase order path uses explicit tri-state error returns. The code-quality debt that most raises AI-agent error rates is concentrated elsewhere: (1) crypto_trading_bot.py drives ~52 module-level globals set inside a 653-line main() and read at call time by the trade functions, which is exactly what blocks the standing "split the file" refactor and forces the AGENTS.md "serialize all work on this file" rule; (2) there is no pytest configuration, so a bare `pytest` from the repo root is broken and, if unbroken, would run live-swap functions outside the network guard; (3) the analysis prompt and provider dispatch are copy-pasted across five files. The dead-code hypothesis in the task mostly did not pan out — the suspect modules are all still wired in — which is itself a good sign.

## Strengths
- Money-path consensus function is well-engineered: process_coin_with_comparison (crypto_trading_bot.py:1166-1402) decomposes into tally_round1/votes_display/decide nested helpers, every branch returns an explicit PanelDecision, and the failure semantics are documented inline against the T3 spec.
- Coinbase order-path error handling is careful, not swallowed: _recover_order (coinbaseutil2.py:383-409) returns an explicit (result, lookup_ok) tri-state distinguishing 'clean failure' from 'unverified failure', and the idempotency contract is documented against the live-validated duplicate shape.
- config.py already contains the clean pattern the bot lacks: a Config dataclass + a single parse_args that folds env+CLI into typed fields — a ready-made template for de-globalizing crypto_trading_bot.py.
- tests/conftest.py socket-level network guard (autouse, function-scoped, fails loud and names the offending test) is a strong testing-hygiene control for an AI-maintained repo.
- Dead-code sweep came back cleaner than the task hypothesized: candidate_util is live behind --export-candidates (crypto_trading_bot.py:2124/2435), fibonacci_analyzer is live via marketdata, and santiment/polymarket/lunarcrush/coingecko are all wired into the runtime or refresh paths — little true orphaning to clean up.

## Findings

### [HIGH/L] crypto_trading_bot.py couples ~52 module-level globals to a 653-line main(), blocking the standing split refactor
**Evidence:** main() (crypto_trading_bot.py:1973) declares 52 distinct `global` names across lines 1983-1998 (TRADING_MODE, LLM_MODE, PRIMARY_LLM, COMPARE_LLMS, REQUIRE_CONSENSUS, INTEGRATION_TIEBREAKER, the four *_trader objects, client, spend_tracker, RUN_ID, ...) and assigns them all in one 653-line body (cyclomatic ~100). The money-path functions read these globals directly at call time: process_coin_with_comparison reads PRIMARY_LLM (1195), LLM_MODE (1202), COMPARE_LLMS (1245), REQUIRE_CONSENSUS (1311), INTEGRATION_TIEBREAKER (1329); get_llm_response (844) reads claude_trader/openai_trader/... These functions have no parameter carrying config — behavior depends on hidden state set 700 lines away.

**Impact:** This is the root cause of the AGENTS.md 'serialize all work on crypto_trading_bot.py' rule and the reason the file can't simply be split: any module you move a trade function into would need to import ~40 mutable globals back from crypto_trading_bot, creating import cycles or a shared-mutable-state hack. It also makes the functions hard to unit-test in isolation (a test must set the right globals first) and makes it easy for an agent to change behavior by editing a global's default without realizing which call sites read it.

**Recommendation:** Do NOT split files first. Stage the refactor as: (1) introduce a frozen BotConfig dataclass (mirror config.py's existing Config) built once in main() from parse_args, and pass it explicitly into process_coin_with_comparison/get_llm_response/the trade gate instead of reading globals — behavior-preserving, landable incrementally, guarded by tests/test_consensus.py. (2) Only after config is threaded, extract the consensus core (process_coin_with_comparison, decide, PanelDecision, _majority_action) into consensus.py — it is the best-tested unit so it moves most safely — and the provider dispatch into a traders/panel module. (3) Extract discovery/filtering wiring last. Keep the four trader objects in a passed-in registry dict rather than four module globals.

### [HIGH/S] No pytest configuration: bare `pytest` crashes on lab scripts and would run live-swap tests outside the network guard
**Evidence:** There is no pytest.ini/setup.cfg/tox.ini/pyproject.toml and no root conftest.py (only tests/conftest.py, whose autouse socket guard covers the tests/ subtree only, per its docstring at conftest.py:81-93). `./venv/bin/python -m pytest --collect-only` from the repo root is Interrupted with 2 collection errors from lab/session_tests_20260718/test_consensus.py:57 and test_extract_rec.py, which execute code at import time (NameError: FAILED_INIT_LLMS not defined). Meanwhile root-level test_trustwallet_swap.py defines pytest-collectable no-arg functions test_with_private_key() (line 267) and test_sell_with_private_key() (line 593) that load a real Solana wallet and POST to SOLANA_RPC mainnet (lines 296-318) — with no network guard because there is no root conftest.

**Impact:** An AI agent that runs `pytest` instead of the documented `pytest tests/` gets a confusing hard failure (collection interrupted, 0 tests run) and wastes time. Latent, more serious: the collection interruption is the only thing currently preventing pytest from invoking the live-swap functions; delete/fix the two lab files and a bare `pytest` would call test_with_private_key against mainnet RPC (and toward an actual swap if SOLANA_PRIVATE_KEY is set), entirely outside the socket guard.

**Recommendation:** Add a minimal pyproject.toml [tool.pytest.ini_options] (or pytest.ini) with `testpaths = ["tests"]` and `norecursedirs = ["lab", "venv", "dex", "context"]` so discovery is scoped to the real suite. Additionally rename the manual scripts that are not pytest tests away from the test_*.py prefix (test_trustwallet_swap.py, test_jupiter_swap.py, test_coinbase.py at repo root, and lab/session_tests_20260718/*.py) — e.g. manual_trustwallet_swap.py — or move them under a non-collected dir, so no naming collision can ever cause them to be collected as unit tests.

### [MEDIUM/M] Analysis prompt text and provider dispatch are copy-pasted across five files
**Evidence:** The core prompt sentence 'sophisticated trading bot designed for short-term appreciation recommend buying, selling, or holding' appears 4x each in claudeutil.py, openaiutil.py, grokutil.py, perplexityutil.py and the inline gemini functions in crypto_trading_bot.py (grep count: 4 per file x 5 files = 20 copies), and the Google-Trends scaling disclaimer is duplicated 2x per file x5. get_llm_response (crypto_trading_bot.py:844-956) then dispatches to these via five near-identical provider branches (peer_analysis x use_trend_check x method-name), ~110 lines that differ only by the trader object. The parallel stack already has a centralized prompts/templates.py, but it is imported only by llm_compare.py (verified), so the runtime traders don't use it.

**Impact:** Changing the analysis prompt, the peer-analysis framing, or the trends disclaimer requires editing the same English in 5 places; if one drifts, panelists are queried with different prompts and the consensus compares votes elicited under non-identical conditions — a subtle money-path correctness risk, only partly pinned by tests/test_framing.py. Adding a new prompt variant means touching 5 near-identical trader methods plus 5 dispatch branches.

**Recommendation:** Extract the prompt bodies into one shared builder (a runtime-side prompt module, or reuse/extend prompts/templates.py) that returns the message string given coin_symbol/peer_analysis/trends_data/market_block; have each trader's send_* method call it and only own the provider API call. Replace get_llm_response's five branches with a registry: a dict {provider: trader_object} plus a small gemini adapter exposing the same send_* interface, then one code path selects method by (peer_analysis, use_trend_check).

### [LOW/S] The provider roster is redefined as ~7 hardcoded literals instead of sourced from modelregistry
**Evidence:** ['gemini','claude','openai','grok','perplexity'] is hardcoded as argparse choices at crypto_trading_bot.py:135, :143, :195, as SINGLE_LLM_MODES at :1021, as the STRUCTURED_VOTE_PROVIDERS subset at :966, and again in config.py:33 (AVAILABLE_LLMS), :49, :137. modelregistry.py already holds the canonical closed set as its MODEL_IDS dict keys (:22-26), and AGENTS.md rule 5 makes modelregistry the single source for provider identity.

**Impact:** Adding or retiring a provider (which AGENTS.md notes happens — grok-4 died within weeks) means finding and updating ~7 scattered literals across two files; miss one and the panel roster, the argparse validation, and the registry disagree.

**Recommendation:** Export a `PROVIDERS = tuple(MODEL_IDS)` (or an explicit ordered tuple) from modelregistry.py and derive SINGLE_LLM_MODES, the argparse `choices=`, and config.py's AVAILABLE_LLMS/defaults from it. Keep STRUCTURED_VOTE_PROVIDERS as an explicit subset since it is a genuinely different fact.

### [MEDIUM/L] Research-tool monoliths carry 900-line, CX>100 main() functions that are effectively untestable
**Evidence:** AST measurement: leading_indicator_tester.py:4728 main() is 913 lines / cyclomatic ~128; correlation_tracker.py:2413 main() is 484 / ~115; leading_indicator_tester.py:3821 run() is 318 / 54. These are imported only by tests and each other (leading_indicator_tester is imported by test files; correlation_tracker by leading_indicator_tester + preflight), i.e. off the live money path, but they are large surfaces an agent will be asked to modify.

**Impact:** A single function of this size with this branch count cannot be reasoned about or unit-tested in pieces; any change is high-risk and forces whole-file serialization, the same failure mode as crypto_trading_bot.py but in tooling that has far less test coverage than the consensus core.

**Recommendation:** Lower priority than the money-path split, but when these tools next need substantive edits, extract the CLI arg-parsing and the top-level command dispatch out of main() into named sub-functions (one per subcommand/mode) so each becomes independently testable. Do not attempt a big-bang rewrite; carve one command handler out at a time.

### [LOW/S] Module-level load_dotenv() is the one remaining import-time side effect, contradicting the documented side-effect-free-import invariant
**Evidence:** crypto_trading_bot.py:16-17 calls load_dotenv() at module scope. AGENTS.md:22 states `import crypto_trading_bot` is side-effect-free. load_dotenv() reads .env from disk and mutates the process-global os.environ at import time. The argparse defaults that need those vars are resolved via os.environ.get(...) inside parse_args(), which runs in main() — so the load could move into main() before parse_args() without changing behavior.

**Impact:** Any importer (including pytest collection of a module that transitively imports the bot) silently mutates os.environ from whatever .env happens to be on disk, which can leak real keys/config into a test process's environment and mildly falsifies the 'import is side-effect-free' guarantee the tests are said to depend on.

**Recommendation:** Move load_dotenv() to the first line of main() (before parse_args()). Confirm the two-line `import crypto_trading_bot` verification in AGENTS.md still passes and that no other module-level code reads os.environ at import.

### [LOW/S] get_config_source mislabels config provenance via substring prefix matching
**Evidence:** get_config_source (crypto_trading_bot.py:301-308) determines a value's source by `for arg in sys.argv: if arg.startswith(arg_name)`. This is a prefix, not equality, so `--coins` would match a hypothetical `--coins-per-run`, and it can't distinguish `--llm-mode` from a longer flag sharing the prefix. It is called ~10 times (2273-2330) purely to print '[--flag]' vs '[ENV env]' vs '[default]' provenance labels.

**Impact:** Display-only, so no trade impact, but the provenance banner an operator/agent reads to confirm 'am I running what I think I am' can be wrong for prefix-colliding flags — misleading during exactly the config-verification step it exists to support.

**Recommendation:** Match the token exactly: check `arg == arg_name or arg.startswith(arg_name + '=')` (argparse accepts both `--flag value` and `--flag=value`). Low urgency; batch with any other parse_args cleanup.

### [LOW/S] Bare `except:` clauses swallow control-flow exceptions in Fibonacci and DEX oracle parsing
**Evidence:** fibonacci_analyzer.py:1105 wraps cached-report display in `except:` (catches KeyboardInterrupt/SystemExit too), and dex/jupiterutil.py:541/544 use bare `except: pass` inside oracle-pubkey parsing, with an outer `except Exception: pass` at 544 that discards any parse error silently. dex/jupiterutil.py has 8 broad except handlers total.

**Impact:** Off the CEX money path (Fibonacci report display and DEX/Jupiter experiments), so low blast radius, but bare `except:` masks Ctrl-C and hides genuinely malformed oracle data as an empty result with no log line, which is hard for an agent to debug later.

**Recommendation:** Narrow the bare `except:` to `except Exception:` at minimum, and log the swallowed error (even at debug level) in the jupiterutil oracle parser so a malformed pubkey list is diagnosable rather than silently yielding partial ChainInfo.
