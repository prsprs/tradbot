The task's own hint was slightly misleading in a useful way: it suggested "a whatif run with `--notional-usd` exceeding `--run-spend-cap-usd` on a forced-BUY" as one option, then immediately noted you can't force a BUY vote from the CLI. That's true, but it also means there is no way to demo the *live-shaped* `[DAILY CAP]` line at all without either an actual BUY vote or calling into the module directly — the CLI genuinely cannot do this, full stop. I spent a few minutes looking for a CLI escape hatch (a `--force-action` flag, a test-mode vote injector) before accepting that "call the production function directly with monkeypatched globals" is not a workaround, it's the only route, and it's also exactly the pattern the repo's own tests already use (`tests/test_run_summary.py`'s `buy_calls` fixture). I should have grepped `tests/test_*` for "how does this repo already fake a BUY decision" before searching for CLI flags — the test suite is the fastest map of "what's actually reachable" in this codebase, faster than reading `main()`'s argparse block.

Second thing that cost time: figuring out which cap line to demo. `maybe_execute_buy` has TWO caps (daily, per-run) and the daily one has genuinely different code paths for live vs. whatif — live fails closed and quarantines on a corrupt ledger, whatif soft-fails and continues. The task asked to observe "the daily-cap REFUSAL," and it took a careful read of the docstring + both branches (lines ~1920-1974 of crypto_trading_bot.py) to realize that only the whatif branch is reachable without an LLM call, since I'm not allowed to set `TRADING_MODE=live` under any circumstance in this repo. That's not a limitation of my demo — it's structural: nothing an agent runs can ever legitimately exercise the live cap-refusal branch. Worth stating loudly in the runbook (I did), because a future reader could mistake the whatif demo's output for proof the live line works identically; it's the same *shape*, not the same *code path*.

One near-mistake: my first draft of `demo_cap_refusal.py` didn't refuse on `LIVE_TRADING_CONFIRMED=1` set-but-`TRADING_MODE` unset — I only checked `TRADING_MODE == 'live'`. Since this script never actually calls `--live`/arms anything (it doesn't touch the CLI at all, it imports the module and calls a function), that specific env var can't do anything harmful here — but AGENTS.md's hard rules are about *any bot run*, and a defense-in-depth refusal costs nothing, so I added the second check anyway before running it for real. Lesson: when writing a new whatif-only entry point, check both live-arming signals (`TRADING_MODE` and `LIVE_TRADING_CONFIRMED`) even if only one is theoretically reachable through that entry point — the cost of the extra guard is near zero and it matches how the rest of the repo treats the double-lock as two independent checks, not one.

I also nearly ran the demo script with `HISTORY_DIR` unset (defaults would have pointed at nothing predictable) before remembering the hard rule about scratch dirs outside the repo — added an explicit refusal-if-missing plus a refusal-if-it-resolves-to-the-repo's-own-`history/` check in the script itself, not just a runbook instruction, since a copy-paste error in the runbook (forgetting to set `HISTORY_DIR`) would otherwise silently write to a location I couldn't predict from the docstring alone. Making the safety check live in the script rather than only in the doc instructions is probably a pattern worth generalizing to future demo scripts in this repo.

What I wish I'd known before starting: `executionledger.spend_today(trading_mode=...)` and `live_spend_today()` are two different entry points into the same underlying `intended_spend_on_date` — I initially assumed there was one function with a mode kwarg used everywhere, and had to re-read `executionledger.py` lines 600-640 to see the live path is a thin `spend_today('live', now)` wrapper kept separate for historical/gate reasons. Not documented anywhere except the docstrings; a one-line note in AGENTS.md ("the ledger has two per-mode spend readers, live_spend_today() and spend_today(trading_mode=...) — they wrap the same underlying sum, don't reimplement one in terms of a hand-rolled filter") would have saved the re-read.

Nothing here rose to the level of a real mistake in the delivered artifact — the closest thing to a dead end was the CLI-flag search above, which cost maybe five minutes before the test-suite grep set me straight.
