The biggest time-saver was reading `process_coin_with_comparison` before assuming I'd need to thread new state through the bot. The task hinted "check whether per-coin final actions are already recorded somewhere reachable" — and they were: both analysis loops (coin-choice and discovery) already call the same function and get back a uniform `PanelDecision` regardless of whether `LLM_MODE` is single-LLM or compare/integrate. I'd half-expected the single-LLM path to be a thinner, separate code path with less to reuse; it isn't, it's the same object with `consensus_state='single'`. Don't assume "single-LLM path" means "different code" — grep the call sites first.

The gate's return value was the detail I almost missed. `gate_and_maybe_buy` already returns `True`/`False` for "was this BUY dispatched to the execution attempt," and that's exactly the signal needed to distinguish `BUY->ordered` from `BUY->gate-blocked` in the vote table — no need to touch `maybe_execute_buy` (which is the riskier, lock-and-cap-heavy function) at all. When a task wants a "did X happen" label, check what the nearest existing function already returns before adding new tracking state.

One honesty gap I had to explicitly document rather than solve: "`->ordered`" means "gate approved and dispatched," not "confirmed filled" — `maybe_execute_buy` can still refuse on spend cap or exclusion after dispatch, and it returns nothing that would let a caller know. I named this precisely in the docstring rather than either overclaiming a fill happened or over-engineering a return-value refactor of a sensitive, well-tested function just for a summary line. If you're tempted to widen a core execution function's contract just to feed a print statement, stop and document the gap instead — smaller blast radius.

Practical snag: I reached for the `Monitor` tool to wait on the background demo-run process, then remembered a subagent has no interactive "later turn" for a notification to land in — `wait <pid>` in the same Bash call blocks correctly and is simpler for a one-shot background job in an agent context. Monitor's docs are written for chat sessions where the user might respond in between; a closeout task running solo should just block.

Tips for the next agent: (1) When a summary/banner needs a value the startup path already computes (like `format_daily_cap_banner_line`), check whether the variable holding the config-source string is still in scope in the same function before reaching for a global — `main()` is one giant function here, so locals from the banner section are still live at the summary print. (2) Follow the existing test file next to the one you're extending almost line-for-line (fixture names, `raising=False` monkeypatching, scratch-ledger redirection) — this repo's suite is dense with precedent and deviating from it just adds review friction. (3) Run the cheap real-API demo in whatif mode with `HISTORY_DIR` pointed outside the repo and actually read the output — it caught that my per-coin label worked end-to-end, not just in the unit tests that construct `PanelDecision` by hand.
